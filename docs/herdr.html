Herdr setup guide

Everything this repo changes or adds on top of stock herdr: the sidebar, the recent-sessions picker, the summarizer plugin, key bindings and the other plugins. Open it with open ~/dotfiles/docs/herdr.html.

The terminal figures are drawn from the real layout with made-up sessions. They are not captures, so nothing from a real session is stored here.

Session names

Each session has a fixed identity, separate from what it is doing at the moment.

  • Three parts: a short name that leads its label (aios orch: awaiting review), a topic of two or three words that names its tab, and a one-sentence purpose shown under the header in the picker preview.
  • Where it comes from: the opening prompt, your messages spread evenly across the session's whole life plus the newest few shown separately, and names it already has: the agent name it was started under and a tab name you typed. The terminal title is not used; Claude Code sets it from the current topic.
  • Orchestrators: a session that started or instructed three or more agents is named as their orchestrator. That is counted from the commands it ran, not judged by the model. Starting an agent or two along the way does not count.
  • What cannot change it: a detour or a delegated side task. Asking the top-level session to start a research agent shows up after the colon as what it is doing, not as a new name.
  • When it is reconsidered: at 1k, 10k, 30k and 100k tokens of conversation, then every 100k, and only if you have said something since the last check. The count is the text you and the agent wrote, not context tokens: tool output and file contents fill the context without saying what a session is for. A turn that crosses two checkpoints is one check. A name is kept unless it was based on only the first message or two, or it no longer fits your recent messages and the opening goal is finished. Each rename is logged with its reason.
  • Telling sessions apart: no two open sessions get the same short name or topic. The model is asked to pick distinct names, and the script checks: a clash is resolved by leading with the session's agent name, or failing that a number. A session keeps a name it already had, so a newer session never pushes an older one off it.
  • Spaces: a space's summary is built from its sessions' topics and purposes, so it does not follow their activity either.
  • Limits per pass: at most three sessions are named in one pass, and a failed attempt waits 15 minutes. Until a session has a name, its label leads with its agent name or the first words of its opening prompt.

Tab names

The summarizer also names tabs, but only the ones you have not named yourself.

  • Which tabs: a tab still carrying herdr's default name (a number) is named after the session in it, in two or three words for its subject, such as aios migration. With several agents in one tab, the first one created there names it, so the name does not flip as other panes become active.
  • Your names win. A tab you named is never touched. If you rename a tab the summarizer named, it lets go of it for good.
  • Handing one back: rename the tab to a number (prefix ,) and it is named automatically again.
  • Stability: the topic can change only at the identity checkpoints described under Session names, never with the session's status. Status stays in the sidebar label.
  • New tabs: herdr asks for a name when you create a tab. Leave it empty to get a number, and so an automatic name. Setting prompt_new_tab_name = false in config.toml skips the question.
  • Off switch: set HERDR_SUMMARIZER_NO_TABS in herdr's environment.

Statuses and dots

Two systems show state, and they answer different questions.

The summarizer's status: where is the work?

StatusMeaning
staleUntouched for a week longer than your newest session. Each stale session is reviewed once by a stronger model against your other sessions, and again only if it moves.
youNeeds you: a decision, information, a review, an action only you can take, or a go-ahead.
workingThe agent is mid-task. A working session that has been silent for 2 hours is shown as idle.
idleStopped without a clear ask; unclear whether anything is left.
finishedThe work was explicitly wrapped up.

herdr's dot: what happened with the last turn?

herdr stateMeaning
doneFinished a turn you have not looked at yet. Becomes idle once you focus the pane.
idleAt the prompt, and you have seen its last turn.
workingMid-turn right now.
blockedStopped at an approval or question dialog.
unknownherdr cannot tell: the agent just started or is gone.

herdr's done is not the summarizer's finished. A session can have an unseen turn and plenty of work left. The orange label is where the two meet: status you plus herdr state done.

How updates happen

Nothing runs on a timer. The plugin subscribes to four herdr events and the rest follows from them.

  1. herdr fires an event. pane.agent_status_changed (a turn started or ended), pane.agent_detected, pane.moved or pane.focused.
  2. The hook returns at once. plugin/hook runs herdr-summarize event, which marks the session dirty and starts a detached worker. herdr waits about 70 ms and never on a model.
  3. The worker checks for a diff. A session is skipped if its transcript file is unchanged, if the new entries are only tool calls, or if the agent is still mid-turn. A pass with nothing new makes no model call.
  4. A small model reads the new turns. Haiku gets the previous label and description plus only the new conversation, and returns the status, who it is waiting on, and your next move. These always follow the latest turn.
  5. The summary changes only when it should. Label and description are rewritten when the new conversation is at least 1,500 characters and the model judges it material, or when work finishes or reopens. Otherwise they stay word for word.
  6. Tokens are published. The label, heat, stale mark and jj status go to herdr as pane and workspace tokens, which the sidebar rows in config.toml display. The jj status is computed during the passes that already run; it adds no event and no timer.
  • Heat and stale need no timer. They depend on the clock, but only matter while you are looking, and switching panes fires pane.focused.
  • Links come from the parent's transcript. herdr events do not say who started a pane, so the summarizer reads the herdr agent … commands a session ran. Agent names are remembered, so a moved or restarted agent stays nested.
  • Nothing is sent to a running agent. Transcripts are read from ~/.claude/projects; the only writes are herdr tokens and the state folder.
  • Cost. One Haiku call per finished turn that has new conversation, and one Opus call per stale session (at most two per pass).

Install and check

./bootstrap.sh                       # stow config and scripts, install plugins and the Claude integration,
                                     # then run validate.sh -q
./herdr-summarizer/install.sh        # opt in to the summarizer (checks herdr, claude, fzf and a claude login)
./herdr-summarizer/install.sh --uninstall
./validate.sh                        # read-only: is everything linked, loading and actually in use?

herdr-plugins status                 # per plugin: pinned, installed, upstream HEAD, commits behind
herdr-plugins check                  # offline; exit 1 when an installed plugin is off its pin
herdr-plugins review <plugin> [sha]  # read-only: commits and install-time code changes, pin to sha
herdr-plugins update [<plugin> [sha]]  # the user's: see below
  • Where pins are read: herdr-plugins reads the bootstrap.sh of the checkout the script is linked from, whatever the current directory. The last line of herdr-plugins help names it.
  • Review: shows the commits, the diff of the manifest and every file its build step runs (any file in the tree that a step, or a file a step names, mentions as a path, to three levels, relative to the repo root or to the naming file, so a python3 tools/dl.py helper counts), the full patch of every other changed text file, and lock-file package changes. Patches share a 1000-line budget and are shown in this order: build-adjacent paths, then the plugin's source and build manifests (.rs, .go, Cargo.toml, go.mod, and any changed file they embed), then everything else (tests, docs, CI, website), smallest first. A bump of ten commits or so usually shows all of the source; a longer one does not, and the largest patches are dropped first. Only binary media (images, audio, video, PDFs, fonts) outside build-adjacent paths are listed by name; a media file under scripts/, build/ or herdr/ makes the review incomplete. It exits 3, incomplete, when it cannot show everything: a file over the budget (the reason says how many lines over and which tiers the dropped files are in), a missing patch, install-time code that fetches something else (see below), a release tag that is not the commit, invisible characters in code. An incomplete review is never a clean one.
  • Update: run it yourself, in a terminal, through ~/.local/bin/herdr-plugins at the main checkout (the first entry of git worktree list, where stow's links point), on a branch you create there. It refuses to start without a terminal, refuses to run from a linked worktree, and reads its confirmations from it. For each plugin: one installed off its pin is first offered a reinstall at the pin; one behind upstream is reviewed, then on yes uninstalled and reinstalled at the new commit without --yes (herdr shows the manifest and build step and asks), and only then is its pin moved in bootstrap.sh. Commit that change afterwards. For a plugin that is not installed here, only the pin moves and nothing is built, so a commit that does not build is found by the next bootstrap. update <plugin> <sha> moves one plugin to that commit instead of upstream HEAD. The sha is 7 to 40 lowercase hex characters, comes last, and follows exactly one plugin; a tag name is not accepted (give the commit it points at). It must be upstream's own, on the default branch's history or the commit a tag points at; GitHub also resolves commits that exist only in forks, and those are refused and counted as a failed update. herdr-plus's build downloads the latest release when Go is missing, so the review requires the release tag to be the target, and the tagged commit is almost never upstream HEAD (the incomplete reason prints the command). Any change to a build script that downloads (herdr-plus's install.sh, reviewr's herdr/install.sh) makes the review incomplete, comment lines included, since a changed build is read as raw text; a change that only adds, drops or rewords whole-line # comments or blank lines does not count.
  • The fetch rule: when nothing in the build changed, its fetches were covered by the review that set the pin (as trusted as that pin was) except ones whose result can change with no change to the repo, which are always incomplete: releases/latest, a raw.githubusercontent.com or /archive/ URL naming a branch, <(curl ...), $(curl ...), eval with curl or wget (on any line, since a URL is often assigned on a line that fetches nothing), and a pipe into a shell or interpreter, a package manager, go install or git clone at command position. Whole-line comments are skipped here. It is a text match on the listed tools, not a shell parse: a fetch by other means or built from variables is not seen. At the current pins, herdr-plus's install.sh sets url=.../releases/latest (line 112) and reads the redirect with $(curl and $(wget, so every herdr-plus review is incomplete for those lines, whatever the target; each reason names the file and line.
  • Incomplete reviews: update leaves the plugin where it is. After reading the compare page, you can pin past it with HERDR_PLUGINS_INCOMPLETE_OK=<7 to 40 leading characters of the commit the run reviews>: the <sha> you gave, else upstream HEAD. If upstream has moved, review again. The override waives every reason at once, not a chosen one, so update prints all of them before it asks to pin; read them, since a genuine one can sit beside the noise. Text quoted inside a reason is the plugin author's, not the tool's.
  • Agents: they may run status, check and review, and never change a pin or what is installed (see CLAUDE.md). To check a worktree's pins, run that worktree's own herdr/.local/bin/herdr-plugins by path; only update refuses to run from a worktree.

After editing config.toml, run herdr config check before reloading with prefix shift+r. The check is what catches mistakes; a reload on its own can report success for a config that has problems.

Run stow --no-folding herdr from the main checkout, never from a worktree. The plugin runs with herdr's environment, so set them there or use them for runs by hand. Each named herdr session keeps its own state under sessions/<name>/. Sessions idle for 30 days are forgotten.

Limits worth knowing

  • Claude sessions only. Summaries come from Claude Code transcripts; other agents show herdr's dot but no label. Proposed: docs/proposals/herdr-summarizer-other-harnesses.md.
  • Links need names. An agent is nested only if its parent drove it through herdr agent commands by name. Agents you start yourself in a new pane are top level.
  • herdr styles tokens statically. A token's colour is fixed in config.toml, which is why the orange label is a second token ($summary_you) sharing a slot with $summary. herdr also always puts · between tokens on a row.
  • The plugin registry is shared by all herdr sessions. A named session (herdr --session sandbox) gets its own server and state, but the same plugins. To test a plugin change safely, list the session names it may act on in ~/.local/state/herdr-summarizer/only-sessions, and delete the file afterwards.
  • jj status is a snapshot. It is read with --ignore-working-copy, so the * lags edits until jj snapshots. A space gets it only when its first pane is in the jj repo.
  • reviewr in jj repos is untested. Whether it works in git, colocated (jj and git) or jj-only repos is for the Phase 6 trial to settle.
  • Pins pin source, not binaries. A release asset replaced after tagging is not detected; the pin and review cover the source and install script.
  • Stale is relative. It compares each session with your newest one, so a week away from the machine does not turn everything stale.
Source of truth is the code: herdr/.config/herdr/config.toml, herdr/.local/bin/herdr-summarize (its header and help text) and herdr-summarizer/, and for the plugins bootstrap.sh and herdr/.local/bin/herdr-plugins (its header and help text). Update this page when those change.
